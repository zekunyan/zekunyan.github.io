前言

ACP 是 LSP 之于 Agent。

MCP 回答了 Agent 能调什么，ACP 回答的是另一组问题：谁来驱动 Agent，prompt 怎么交进去，过程怎么流式回推，写文件之前怎么先确认一次，这一轮什么时候算结束。

当年 LSP 把编辑器和 language server 解耦，编辑器不用为每种语言重写一套补全和跳转。ACP 做的是同一件事，对象换成了 coding agent：宿主实现一次 Client，Agent 实现一次 Server，任意组合直接通。

问题：没有统一协议时，宿主 × Agent 是乘法

每个 Agent 的会话、流式输出、权限确认、diff 展示各不相同，宿主每接一个 Agent 就要重做一遍集成。

没有 LSP 之前，编辑器支持一门语言就要单独写一套插件，补全、跳转、诊断都跟语言绑死，组合一多就失控。LSP 之后规矩变了：编辑器只实现一次协议，language server 只实现一次协议，中间对上就行。

Agent 现在处在类似阶段：

没有 ACP：  M × N
            5 个宿主 × 8 个 Agent = 40 套定制集成
            会话、流式渲染、权限弹窗、diff 展示，每套重写

有了 ACP：  M + N
            5 + 8 = 13 次实现
            宿主实现一次 Client，Agent 实现一次 Server

数字是示意，讲的是组合方式的变化。价值不只是省插件，更是选型自由：同一个 Agent 嵌进自研工具或内部平台，只要对面支持 ACP，Agent 侧不用改；反过来换 Agent，UI 和会话层也不用重做。

ACP 是一层协议，位置很具体：在宿主和 Agent 之间。下面先划边界，再讲它定义了什么，最后看一个最小 demo。

划边界：ACP 不管什么

边界不划清，后面很容易把 ACP 当成万能层，什么都往里塞。

不管工具。 ACP 不定义工具。Agent 内部能调什么工具、工具怎么实现，是 MCP 和 Agent 自己的事。ACP 只管会话怎么开、prompt 怎么交、过程怎么流回来、要权限时怎么问。

不管模型。 Agent 内部怎么调模型、用哪个模型、上下文怎么拼，ACP 都不管。它看到的是会话和消息，不是推理过程本身。

不是另一个 ACP。 IBM / BeeAI 有个同名的 Agent Communication Protocol，已经并入 A2A。本文的 ACP 只指 Zed 发起的 Agent Client Protocol，不要对错文档。

一句话收住：ACP 回答的是“谁来驱动 Agent、怎么管它”，不是“Agent 能调什么”。后一个问题是 MCP 的地盘，后面有一节专门对照。

ACP 是什么：一套跑在 stdio 上的 JSON-RPC 会话协议

ACP 全称 Agent Client Protocol，标准化的是 Agent 宿主和 coding agent 之间的通信。协议里宿主统称 Client，可以是 code editor、IDE、编排应用、自研平台。

宿主把 Agent 当子进程拉起来，双方通过 stdin / stdout 交换 newline-delimited 的 JSON-RPC 2.0：一行一条 JSON，不开端口，不起 daemon，抓 stdout 就能 debug。

消息是双向的，这一点很关键。宿主调 Agent 的同时，Agent 也能反过来调宿主：要权限、读宿主里还没保存的文件、在宿主里开终端，都走反向请求。后面看报文时，这一点会很直观。

图 1：四条协议各管一段。AG-UI 管界面到宿主，ACP 管宿主到 Agent，MCP 管 Agent 到工具，A2A 管 Agent 到 Agent。四条都是公开标准，差别只在连的是谁，能叠着用，不是互相替代。同一次会话里几条线经常同时在跑，比如 session/new 的参数里就带着 mcpServers。

几个关键事实：

  • 传输： JSON-RPC 2.0、newline-delimited、stdio，不开端口。稳定版 protocolVersion: 1；v2 是 2026-07-20 发布的草案，生产按 v1 写，不要按草案押注。
  • 来历： Zed 在 2025-08-27 发布，Gemini CLI 是第一个参考实现；JetBrains 在 2025-10 加入共建；Registry 在 2026-01-28 上线。
  • SDK： 覆盖 Rust / TypeScript / Python / Kotlin / Java，其中 Rust 与 TypeScript 在 2026-06 到 1.0。自己写宿主时，优先看这两个。
  • 生态量级： Registry 里已经有几十个 Agent 和 Client，具体数字变化很快，不要记死一个数。1

一次会话怎么跑：握手、建会话、一轮 prompt

所有 ACP 会话都是同一个骨架。看懂这张时序图，协议的大部分内容就通了，剩下的大多是可选 capability。

图 2：一次会话时序。最容易误解的是第 3 步和第 6 步的关系：session/prompt 是一个长开着的请求，Agent 一边处理一边用 session/update 推进度，整轮结束才回响应和 stopReason。权限和文件读写则是有 id 的反向请求，宿主必须回复，不回 Agent 就一直等。

报文长什么样：四段就够了

下面四段按 v1 规范精简，关键点标在每段前面。

第一段，initialize。先报家门，id 为 0，没声明的 capability 就是不支持。

// Client -> Agent
{"jsonrpc":"2.0","id":0,"method":"initialize","params":{
  "protocolVersion":1,
  "clientCapabilities":{
    "fs":{"readTextFile":true,"writeTextFile":true},
    "terminal":false},
  "clientInfo":{"name":"my-client","version":"0.1.0"}}}

// Agent -> Client：回版本、能力、登录方式
{"jsonrpc":"2.0","id":0,"result":{"protocolVersion":1,
  "agentCapabilities":{"loadSession":true},
  "authMethods":[{"id":"opencode-login","name":"Log in with OpenCode"}],
  "agentInfo":{"name":"opencode","version":"..."}}}

第二段，session/new。cwd 必须是绝对路径，可带 mcpServers。

// Client -> Agent，id=1
{"jsonrpc":"2.0","id":1,"method":"session/new","params":{
  "cwd":"/Users/you/acp-demo/demo_workspace",
  "mcpServers":[]}}

// Agent -> Client
{"jsonrpc":"2.0","id":1,"result":{"sessionId":"sess_9f3..."}}

第三段，session/prompt 加 session/update。请求长开，通知流式回推。

// Client -> Agent，id=2；这个请求一直开着，直到整轮结束
{"jsonrpc":"2.0","id":2,"method":"session/prompt","params":{
  "sessionId":"sess_9f3...",
  "prompt":[{"type":"text","text":"在当前目录新建 hello-acp.md ..."}]}}

// Agent -> Client，通知（无 id）：plan
{"jsonrpc":"2.0","method":"session/update","params":{"sessionId":"sess_9f3...",
  "update":{"sessionUpdate":"plan","entries":[
    {"content":"新建 hello-acp.md","status":"in_progress"},
    {"content":"写入介绍","status":"pending"}]}}}

// Agent -> Client，通知（无 id）：tool_call
{"jsonrpc":"2.0","method":"session/update","params":{"sessionId":"sess_9f3...",
  "update":{"sessionUpdate":"tool_call","toolCallId":"call_1",
  "title":"Write hello-acp.md","kind":"edit","status":"pending"}}}

// 整轮结束，id=2 的响应才回来
{"jsonrpc":"2.0","id":2,"result":{"stopReason":"end_turn"}}

第四段，session/request_permission。Agent 反过来问宿主，两边各自编号。

// Agent -> Client，有自己的 id，必须回复
{"jsonrpc":"2.0","id":0,"method":"session/request_permission","params":{
  "sessionId":"sess_9f3...",
  "toolCall":{"toolCallId":"call_1","title":"Write hello-acp.md"},
  "options":[
    {"optionId":"allow_once","name":"Allow once","kind":"allow_once"},
    {"optionId":"reject_once","name":"Reject","kind":"reject_once"}]}}

// Client -> Agent：对应权限卡片，点 Allow once 才回这条
{"jsonrpc":"2.0","id":0,"result":{
  "outcome":{"outcome":"selected","optionId":"allow_once"}}}

这个地方要注意：第四段里 Agent 侧的 id: 0 和第一段里宿主侧的 id: 0 不冲突。stdio 是全双工的，两边各自编号。写宿主时容易踩的坑，是拿一个全局字典装所有响应，请求和反向请求会撞号。分开两个表就没有这件事了。

session/update 常见的几种：agent_message_chunk 是正文流式片段，逐段追加；agent_thought_chunk 是思考片段，一般折叠；plan 渲染成任务清单；tool_call / tool_call_update 带工具动作和 diff 内容块，编辑器里的 diff 视图就来自这里。完整 schema 以官网为准，这里只列常用的几种。

ACP vs MCP：管会话和管工具，是嵌套不是二选一

这一节只讲和 ACP 对照需要的部分。

MCP 是 Anthropic 在 2024-11 开源的，三个原语：Tools 是能做的事，带 JSON Schema 的函数，模型决定调用；Resources 是能读的数据，URI 寻址、只读，由应用决定何时塞进上下文；Prompts 是可复用的模板，用户显式触发，实际采用率最低，了解即可。

MCP 的传输同样是 JSON-RPC 2.0，两个协议在设计语言上接近，ACP 的 content blocks 还直接复用了 MCP 的类型。

对照ACPMCP
连接谁宿主（Client）↔ Coding AgentAgent ↔ 工具与数据（MCP Server）
回答的问题哪个 Agent，在哪个界面里跑，怎么管它这个 Agent 能碰什么、能调什么
Agent 的角色被驱动的一方（Server）消费工具的一方（Client）
核心方法initialize、session/new、session/prompt、session/update、session/request_permissioninitialize、tools/call、resources/read、prompts/get
状态有状态，session 贯穿多轮以单次调用为主
传输stdio（v1），远程传输仍在规范中stdio / Streamable HTTP

两者怎么拼，一句话就够：session/new 可以携带一组 mcpServers，外层 ACP 管会话，内层 MCP 管工具。后面 demo 里勾上 MCP 开关的那一步，看到的就是这个嵌套。

A2A 和 AG-UI：只讲边界

这两条不展开，只把和 ACP 的边界划清，选型时不至于拿错。

A2A：Agent ↔ Agent，黑盒委派。 Google 发起，解决跨框架、跨厂商的 Agent 怎么发现彼此、委派任务。核心是 Agent Card（JSON 数字名片）加 Task（有状态的工作单元）。对面是黑盒，不暴露内部记忆与工具，这是它敢跨公司用的前提。MCP 是纵向，Agent 到工具；A2A 是横向，Agent 到 Agent。

AG-UI：Agent ↔ 用户界面，HTTP 事件流。 CopilotKit 发起，把 Agent 的运行过程标准化成一条 HTTP 事件流，任意前端都能渲染，1.0 已冻结。它最容易和 ACP 混：两者都在把过程流式推给界面、能反向要权限，但 AG-UI 走 HTTP、连任意框架的 Agent；ACP 是本地 stdio、一个宿主驱动一个 coding agent。范围不同，不要互相替代。

对应关系其实很整齐：session/update 约等于 AG-UI 的事件流，session/request_permission 约等于它的 interrupt，fs/* 反调约等于 frontend tools。理解了一条，另外一条学起来很快。

最小 demo：一个 bridge.js，左栏干活，右栏看协议

这是一个本地可跑的最小 demo，验证的是“换 Agent 只改一行”，不是生产系统。

实现很克制：Node.js 标准库、不装依赖，一个 bridge.js 跑在 localhost:8000。浏览器拉不起子进程，所以中间夹一层桥：对浏览器走 HTTP / SSE，对 Agent 走 stdio JSON-RPC。只有桥到 Agent 这一段是 ACP，浏览器那段不是。

图 3：demo 架构。桥做两件事：吐页面，以及把 stdio 上的 JSON-RPC 转成 SSE 推给浏览器、把浏览器的 POST 写回 Agent 的 stdin。MCP 开关打开时，session/new 会把一个叫 demo-time 的 MCP server 一并递给 Agent，Agent 自行拉起它。

前置条件是登录要自己先做完，桥不替登录：

Agent桥 spawn 的命令前置
opencodeopencode acp先 opencode auth login
Qoder CLIqoder --acp先跑一次 CLI 本体登录，IDE 登录不算

跑起来就三步：

  1. 启动 Agent，看握手亮起。 选 opencode 点“启动 agent”，右栏 initialize、session/new 依次亮起，这两步由桥自动完成。
  2. 点预设，看权限往返。 点“新建 hello-acp.md”，权限卡片弹出时点 Allow once，Agent 才继续写盘。这就是 session/request_permission 的一次完整往返，点 Reject 它就停。
  3. 勾 MCP 开关，看嵌套。 勾上 MCP 后再建会话，能在报文里看到 session/new 把 demo-time 这个 MCP server 递进去。然后换 Qoder 再跑同一句，页面一行不改。

这个 demo 证明的不是 Agent 有多强，而是接口换人不用重做。Agent 强不强是另一回事，下一节就讲。

什么时候值得上，什么时候先不用

值得上：

  • 要把 coding agent 嵌进自己的产品：内部平台、IDE 插件、自研工具、App。
  • 想保留换 Agent 的自由，不被某一家 CLI 的私有输出格式绑住。
  • 需要结构化地拿到 plan、tool_call、diff、权限请求，而不是解析终端文本。
  • 做多 Agent 编排的 UI 层：一个宿主驱动多个 ACP Agent。

先不用：

  • 只是日常用现成 Harness 写代码：ACP 在底层跑着就行，不必自己实现宿主。
  • 只需要 Agent 调工具：那是 MCP 的事，单独接 MCP server 即可。
  • 需要远程、多租户：v1 只有本地 stdio，不要拿它押注，见限制一节。

往工作流方向看，ACP 给的是驾驶座，不是工作流引擎。中间过程变成结构化事件、危险动作前有协议级的闸门，这两点对编排有用；但编排、状态、重试、审计要再搭一层。先把单步的会话和权限跑稳，再谈把多步流程压到它上面，不要一上来就先做平台。

限制：这几条不写清，接入时迟早踩到

ACP 解决的是接口问题。接口之外的问题，它一个都不解决。

  • 管不了 Agent 能力强弱。 效果差异来自 Agent 和模型本身。换协议不会让一个弱 Agent 变强，两个 Agent 跑同一句 prompt，产出质量该差还是差。
  • 支持 ACP 不等于支持全部 ACP。 各家对可选 capability 的支持参差：有的不支持 session/load，有的终端能力没开。接入前先看 initialize 的响应，以它为准，不要看宣传页。
  • 头部 CLI 本体不支持 ACP。 Claude Code、Codex 本体不支持 ACP，走的是社区 adapter，现在是 @agentclientprotocol/* 下的 claude-agent-acp / codex-acp。能用，但多一层就多测一层，升级时先测 adapter 再测本体。
  • v1 只有本地 stdio。 远程、多租户场景不要拿 v1 押注。真要远程，等规范把远程传输定下来，或者自己在桥那一层想清楚认证和隔离，不要假装 stdio 能直接搬到线上。
  • 不给编排语义。 ACP 不给 DAG、持久化、重试、达标判定。stopReason 只说明这一轮结束了，不说明做对了。做没做对要靠宿主侧的验收，比如文件在不在、测试过不过，那是编排层的事。

总结

总的来说：

  1. ACP 是宿主和 Agent 之间的会话协议，位置对应 LSP 当年在编辑器和语言之间的位置，解耦靠的就是这一层。
  2. 它和 MCP 是嵌套关系：外层管会话和权限，内层管工具，日常选型时先分清自己缺的是哪一层。
  3. 值不值得自己实现宿主，取决于是否要嵌、是否要换 Agent；只是日常写代码的话，用现成 Harness 就够了。
  4. 今天落地按 v1、按本地 stdio、按 initialize 的实际响应来；远程和编排等规范与上层实现都准备好再说。
